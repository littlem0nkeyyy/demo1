01 · The problem

AI can find products.
Can we trust the answer?

Natural language

Buyers describe needs such as: “neutral running shoes, wide fit, under 160 AUD.”

Multiple merchants

The same product can have different prices, delivery times and stock across offers.

Merchant control

Not every internal fact should become a claim made to the buyer.

The central question: how can an agent choose better without inventing reasons or leaking merchant data?

05 · Ranking

“Match first, utility second”

Stage A

Verified requirements

Candidates with more confirmed requirements always rank higher — even if another product is cheaper or faster.

VERIFIED_MATCHVERIFIED_NON_MATCHUNKNOWN
Stage B

Cold-start utility

Within the same verified-match bucket, balance:

Relevance40%
Price25%
Trust20%
Fulfillment15%

Relevance = 60% attribute match + 40% semantic similarity. Fulfillment = 70% delivery + 30% shipping fee.

A better requirement match cannot be out-ranked by a cheaper price.

06 · CONTROL

The merchant decides
which facts are visible

AGENT_VISIBLEFact, evidence and match status flow to the buyer agent and may appear in decision factors.
MATCHING_ONLYUsed internally for ranking, but exposed as UNKNOWN and omitted from the reason.
INTERNAL_ONLYExcluded from matching and never surfaced on any agent-facing surface.

Disclosure is enforced at one response boundary — not through scattered checks.

CONTROL = matching power ≠ disclosure power6 / 11

10 · Validation & reliability

Built to be tested,
not just demoed

Core invariants

• Fact decisions, search results and ranking impressions/actions are append-only.
• Evidence NONE forces value = null.
• Product scope is checked consistently in all three product-id tools.
• Pure ranking functions are unit-testable without an API key.

Validation Lab

Compare baseline and enriched runs on the same held-out queries, embedding model and catalogue.

Only make a claim when both runs are valid.

Current limitation

The committed dataset has no held-out query fixtures yet. The Report page correctly asks for baseline and enriched runs. This is a data-authoring gap, not a code bug.
